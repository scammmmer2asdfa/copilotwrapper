What this app actually does under the hood, for people who want more than "it opens Codespaces."

Signing in and opening a codespace Embedding the editor Terminal Quick browse Security model Why an app, not a tab

Signing in and opening a codespace

The "+" button in the icon rail opens a new tab pointed at github.com/codespaces — an ordinary page rendered in an isolated Electron <webview>. You sign in there exactly like you would in any browser (no separate app sign-in flow, no device codes, no CLI). Clicking a codespace in that list navigates the same tab to that codespace's own github.dev editor — the app just watches the webview's own did-navigate/page-title-updated events to keep the tab's persisted URL and title in sync, it never calls a GitHub API directly.

Embedding the editor directly

Once you open a codespace from the github.com/codespaces list, that page navigates to something like https://<codespace-name>.github.dev — all inside the same Electron <webview> tab. That's the exact same web editor GitHub serves at that URL — nothing about the editor itself is modified, proxied, or reimplemented. What's different is where it's rendered: inside a dedicated native window instead of a browser tab, so the browser's own reserved keyboard shortcuts never get a chance to intercept a keystroke meant for the editor.

The embedded terminal

The bottom panel's Terminal tab is a real, PTY-backed shell — node-pty in the main process spawns an actual bash/powershell.exe process, and xterm.js renders it in the renderer, the same combination VS Code's own integrated terminal uses. It runs entirely independently of any open codespace tab — it's a local shell on your own machine, not a shell inside a codespace.

Right Shift: quick, transient browsing

Pressing Right Shift alone (not as part of a combo like Shift+Tab — tracked via keydown/keyup, not a single keypress check) toggles a small popup: a URL bar plus back/forward/reload, backed by its own separate <webview>. It's deliberately not persisted across restarts and not added as a permanent tab — it's meant for a quick "let me check something" without leaving the app, not a second browsing session to manage.

Security model

The renderer process has nodeIntegration: false and contextIsolation: true. It has no direct access to Node.js, Electron internals, or the filesystem — every capability it has is a specific, typed method exposed through contextBridge in src/preload/index.ts, backed by an explicit IPC channel list in src/shared/ipc.ts (listing/persisting tabs, the terminal, settings). The <webview> tags used for tabs and the quick browser are separate, isolated webContents with no access to that bridge and no Node integration of their own — they're just displaying whatever page they're pointed at, the same as a browser tab would. The app itself never sees, stores, or transmits your GitHub credentials — signing in happens entirely inside that isolated webview, the same as signing into any site in a regular browser.

Why an app instead of a browser tab

Browsers reserve a lot of keyboard shortcuts for their own chrome — new tab, close tab, switch tab, open settings — and a page running inside the browser (including a full VS Code instance like the Codespaces web editor) never sees those keystrokes at all. That's a real, widely reported annoyance for browser-hosted editors specifically. A dedicated Electron window doesn't have that browser chrome in the way; the embedded editor gets first access to keyboard input the same way a native desktop app would.

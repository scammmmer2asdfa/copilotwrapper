The protocol: ACP, not screen-scraping

The official Copilot CLI ships an --acp flag that starts it as an Agent Client Protocol server, speaking newline-delimited JSON-RPC over its own stdin/stdout. Copilot Desktop's Electron main process spawns exactly that process and talks to it directly — there is no terminal emulator parsing colored text, no regular expressions guessing when a response is "done," and no separate reimplementation of chat logic. The methods this app calls are the same ones any ACP-speaking client would:

  • initialize — capability + auth-method negotiation, done once per process.
  • session/new — creates a session for a working directory; the CLI immediately starts pushing session/update notifications, including the list of native slash commands available in that session.
  • session/prompt — sends a user turn; resolves once the agent's turn is fully finished (its actual output arrives incrementally via notifications while this is pending).
  • session/cancel, session/set_mode — interrupt a turn, or switch between the CLI's own Agent / Plan / Autopilot modes.

Two kinds of messages flow the other way: session/update notifications (agent message/thought chunks, plans, tool call start/update events) that this app folds into a single growing chat log rather than one bubble per network chunk, and inbound session/request_permission requests — the agent itself asking permission before running a tool — which this app turns into a blocking modal dialog. Nothing proceeds in that session until the dialog is answered or cancelled.

The send queue: why messages never get dropped

session/prompt is a single in-flight call per session — you can't fire a second prompt while the first is still resolving without it interrupting the running turn. But people don't wait; they keep typing follow-ups while the agent is still working. Copilot Desktop handles this with a small SQLite-backed queue (src/main/db.ts, src/main/agent-manager.ts):

  1. Every sent message is written to a messages table immediately, so the log is always accurate regardless of send timing.
  2. If no turn is in flight for that session, the message is dispatched right away.
  3. If a turn is in flight, the message is inserted into a queue table with status queued instead.
  4. When the in-flight turn resolves, the queue is drained for that session — one item at a time, in insertion order, each marked sending right before dispatch and sent (or failed, without blocking anything behind it) after.

The important part: if the app crashes or is killed while an item is marked sending, that item is not lost. openDatabase() resets any row still marked sending back to queued the next time it opens — so the message gets retried instead of silently disappearing. This exact behavior is covered by an automated test that reopens the database mid-"crash" and asserts the row comes back as queued.

Sign-in: zero tokens in this app

This app never sees, stores, or transmits a Copilot access token. The CLI's own initialize() response includes an authMethods list, and each method carries a _meta['terminal-auth'] object with the exact command and arguments the CLI wants run to authenticate — in practice, copilot login. All this app does is spawn that exact command as its own child process and scrape the device-code and verification URL it prints to stdout/stderr for display in a dialog. The actual OAuth device-code exchange, and the resulting token, live entirely inside that CLI process and whatever credential store it uses on your machine.

Choosing which CLI binary runs

Settings → "Copilot CLI location" lets you point the app at a copilot binary you installed yourself (for example via npm install -g @github/copilot) instead of the one bundled with the app. Two reasons you might want this: you already keep the CLI updated yourself and want the app to use that exact version, or you're hitting macOS Gatekeeper's quarantine block on the downloaded app bundle — an npm-installed binary is never quarantined the way a browser-downloaded file is, so pointing at one sidesteps that specific problem entirely for the CLI process (the app bundle itself still needs the usual "Open Anyway" workaround once).

The embedded terminal

The bottom panel's "Terminal" tab is a real, PTY-backed shell — node-pty in the main process spawns an actual bash/powershell.exe process per terminal, and xterm.js renders it in the renderer, the same combination VS Code's own integrated terminal uses. Keystrokes go renderer → IPC → PTY; PTY output goes the other way. It is entirely independent of the agent session running alongside it — you can run your own commands without touching what the agent is doing. The "Agent Output" tab next to it is different: it's a live, read-only stream of the copilot --acp subprocess's own stderr, useful for seeing what the agent process itself is logging in real time.

Agent instructions

Settings → "Agent instructions" reads and writes .github/copilot-instructions.md in the current session's working directory — the same repo-level rules file the real CLI's own instruction loading (and its /init slash command) uses. This app doesn't invent a separate rules format; it just gives you a convenient editor for the file the CLI already reads.

Security model

The renderer process has nodeIntegration: false and contextIsolation: true. It has no direct access to Node.js, Electron internals, or the filesystem — every capability it has is a specific, typed method exposed through contextBridge in src/preload/index.ts, backed by an explicit IPC channel list in src/shared/ipc.ts. The renderer can ask the main process to "open this file in an editor" or "start a terminal at this path," but it cannot execute arbitrary Node code, and window navigation to external URLs is intercepted and redirected to your OS's default browser rather than loaded in-app.

Why the CLI binaries are committed to this repo

resources/copilot-cli/ contains the actual copilot executables for all four supported platforms, tracked with Git LFS rather than fetched from npm at build time. A clone of this repository (with Git LFS support) is a complete, working development environment with no separate download step and no dependency on the npm registry being reachable at build time. scripts/fetch-cli.mjs still exists — it's how these vendored binaries get updated to a newer published CLI version, not how they're obtained for day-to-day development.

What this app actually does under the hood, for people who want more than "it opens Codespaces."

Listing codespaces Embedding the editor Terminal Quick browse Security model Why an app, not a tab

Listing your codespaces

The "+" button in the icon rail shells out to gh api user/codespaces — the raw GitHub REST API via the gh CLI you already have installed and signed in. This app deliberately does not use gh codespace list --json for this, even though it's the more obvious command: that command's JSON output doesn't include a web_url field (verified against the real CLI's own documented JSON fields before writing this code), and that URL is exactly what gets embedded in the app. The raw API response does include it, so that's what this app calls instead.

Embedding the editor directly

Each codespace's web_url (something like https://<codespace-name>.github.dev) goes straight into an Electron <webview> element as a tab. That's the exact same web editor GitHub serves at that URL — nothing about the editor itself is modified, proxied, or reimplemented. What's different is where it's rendered: inside a dedicated native window instead of a browser tab, so the browser's own reserved keyboard shortcuts never get a chance to intercept a keystroke meant for the editor.

The embedded terminal

The bottom panel's Terminal tab is a real, PTY-backed shell — node-pty in the main process spawns an actual bash/powershell.exe process, and xterm.js renders it in the renderer, the same combination VS Code's own integrated terminal uses. It runs entirely independently of any open codespace tab — it's a local shell on your own machine, not a shell inside a codespace.

Right Shift: quick, transient browsing

Pressing Right Shift alone (not as part of a combo like Shift+Tab — tracked via keydown/keyup, not a single keypress check) toggles a small popup: a URL bar plus back/forward/reload, backed by its own separate <webview>. It's deliberately not persisted across restarts and not added as a permanent tab — it's meant for a quick "let me check something" without leaving the app, not a second browsing session to manage.

Security model

The renderer process has nodeIntegration: false and contextIsolation: true. It has no direct access to Node.js, Electron internals, or the filesystem — every capability it has is a specific, typed method exposed through contextBridge in src/preload/index.ts, backed by an explicit IPC channel list in src/shared/ipc.ts (listing/opening codespaces, the terminal, settings). The <webview> tags used for codespace tabs and the quick browser are separate, isolated webContents with no access to that bridge and no Node integration of their own — they're just displaying whatever page they're pointed at, the same as a browser tab would.

Why an app instead of a browser tab

Browsers reserve a lot of keyboard shortcuts for their own chrome — new tab, close tab, switch tab, open settings — and a page running inside the browser (including a full VS Code instance like the Codespaces web editor) never sees those keystrokes at all. That's a real, widely reported annoyance for browser-hosted editors specifically. A dedicated Electron window doesn't have that browser chrome in the way; the embedded editor gets first access to keyboard input the same way a native desktop app would.
